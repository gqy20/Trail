# Trail

把 Chrome 标签页分组记录成一次可保存、可回看、可继续整理的研究轨迹。

## 使用流程

1. 在 Chrome 中打开一组调研页面，最好先放进同一个 Tab Group。
2. 点击 Trail 插件图标，直接打开侧边栏的“研究路径”，确认记录名称。
3. 点击“开始记录”。
   当前页未分组时，可在边栏勾选多个网页，再点击“新建分组并记录”；仅所选网页进入新分组。“记录当前窗口”直接生成整个窗口的记录，不受勾选影响。
4. 正常浏览、选中、复制和点击资料链接。
5. 点击“生成文档”，Trail 会保存本次研究记录并在边栏显示摘要；点击“展开文档”进入完整文档页。
6. 在研究文档页补充调研目标，查看来源、关注片段和折叠的调研路径。
7. 需要时编辑、保存、复制或导出 Markdown；准备接入 AI 时可导出“AI 输入”JSON。

研究路径首页显示最近 3 条记录。“全部记录”在当前边栏内打开，可搜索名称、来源和关注片段，重命名或删除记录；点击记录进入摘要，返回时保留搜索条件。交互捕获设置默认折叠。

## 交互捕获

Trail 只在录制期间捕获普通网页中的交互信号，不读取系统剪贴板，也不会记录输入框、文本域或可编辑区域中的内容。

当前支持：

- 复制捕获：用户在网页内选中文本并复制后，保存为“已复制”片段。
- 稳定选中：用户选中文本并停留片刻后，保存为“仅选中”关注片段。
- 复制升级：如果用户先选中、随后复制同一段文本，Trail 会把原片段升级为“已复制”，避免重复记录。
- 点击路径：用户点击搜索结果、外链、文档目录、GitHub 或下载链接后，保存为调研路径。
- 来源分级：Trail 会根据停留、选中、复制、链接点击和回访次数，粗略区分核心来源、参考来源和过渡页面。
- 上下文记录：可记录页面标题、URL、domain、章节标题、附近文本和大致页面位置。
- 片段治理：支持类型识别、重复复制合并、域名排除和可选自动脱敏。

相关开关在侧边栏“研究路径”的“交互捕获”面板中：

- 记录网页复制
- 记录稳定选中
- 记录链接点击
- 保留来源上下文
- 复制后轻提示
- 合并重复片段
- 自动脱敏
- 不记录当前域名

自动脱敏默认关闭；开启后会在写入 `chrome.storage.local` 前隐藏常见邮箱、token、密钥和 API key 形态。

## 保存与导出

- 结构化记录保存在扩展自己的 `chrome.storage.local` 中，这是当前的事实数据源。
- 研究文档页的“保存”会把人工编辑后的 Markdown 写回本地记录。
- “导出”会下载 Markdown 文件，并记录最近导出的文件名和时间。
- “AI 输入”会导出版本化的 `ResearchReportInput` JSON，包含调研目标、来源、关注片段、点击路径和计数摘要。

下一阶段如果需要稳定写入 Obsidian、指定本地目录或团队知识库，可以在当前数据结构上增加本地文件夹授权或云端同步，而不改变采集逻辑。

## AI 接入准备

当前版本还没有直接调用 AI。接入前先做这些准备：

- 用 `ResearchReportInput` 作为模型输入契约，而不是直接把 UI 或整篇 Markdown 丢给模型。
- 给来源、证据片段和点击路径生成稳定 ID，方便模型输出引用。
- 控制输入长度，片段和上下文会做裁剪，避免无边界发送网页内容。
- 保留调研目标字段，让模型知道“这次要回答什么问题”。
- 继续保留人工编辑的 Markdown，AI 失败时仍然可以使用规则生成和手动整理。
- 后续真正接模型时应通过自有后端调用，不把 API key 放进扩展。

## Browser Tool

侧边栏将日常任务与规则管理分开：

- **网页工具**：选择工具，对当前网页执行或导入本次批量输入；运行参数和本次结果都在这里。文献提取结果可直接加入文献队列，已有文献的下载和筛选状态会保留。
- **账号采集**：维护长期账号名单、设置采集间隔并管理 GitHub 发布配置；支持 TXT/CSV 或粘贴批量导入、导出和批量删除，采集结果进入发布暂存。
- **日志**：通过“运行日志／文献队列”标签切换。运行日志按平台、级别、区域和关键词筛选；文献队列支持导入外部 CSV、去重、筛选和处理全文，导入新文件会先确认替换当前队列。
- **设置 → 工具库**：同步内置规则或添加 YAML。导入前展示适用网站、用途和同 ID 替换影响；手动导入后规则转为自定义，不再被内置同步覆盖。运行参数不属于全局设置。

恢复内置规则时，自定义副本保存在“规则备份”中，可导出 YAML，备份不参与运行或自动任务。自定义规则内容变更后，自动任务需重新确认；内置采集规则更新会同步已有定时授权。

工具库中每个工具可独立停用。停用会从业务列表隐藏工具并关闭其自动任务，规则、名单和历史保留；内置同步或规则更新会保留停用状态。重新启用不会恢复自动任务，需要单独开启。运行中的任务需先结束或停止。

设置中的“采集预算”按平台独立限制近 24 小时访问尝试，默认每个平台 6 小时等效浏览量（360 分钟）：主页 2 分钟、详情 1 分钟，两者共用该平台额度；例如 60 个主页加 240 篇详情达到 360 分钟。它是内容浏览量模型，并非实际执行时长或站点允许量。默认主页最小访问间隔 15 秒、详情 5 秒，与工具规则的等待同时生效。预算不足保存批量进度，不触发登录验证冷却；额度逐笔释放，调整预算或恢复后手动继续。普通网页批量检索不消耗社交采集额度。旧版混合账本无法准确归属平台，升级后保留原账本，使用新的平台账本重新计量。

项目包含一个与研究记录核心解耦的声明式浏览器工具运行时。它可以在用户已登录的普通网页中执行受限的填写、点击、等待、翻页和 DOM 提取工作流，适合后续接入知网、Web of Science 等网页检索平台。

- 工具使用 YAML 定义，后台和 content script 都不执行 YAML 中的任意 JavaScript。
- 支持域名与 URL 匹配、参数模板、有限循环、结构化字段提取和内置转换。
- 工具可在 YAML 中声明独立的展示契约，工作区标题、输入、参数布局、结果名称和字段顺序不写入 Trail 核心。
- 批量输入支持直接放置多条检索词，也可由 YAML 启用多词组组合器，按 AND/OR 等平台允许的连接符生成并预览检索式。
- 结果可以由 YAML 声明详情页全文资源，用户勾选后按 PDF/CAJ 等格式串行下载；验证码、登录和权限页面会暂停处理。
- Side Panel 的“日志 → 文献队列”可导入独立文献 CSV，识别 `title`、`doi`、`pdf_url`、`download_url`、`decision`，按 DOI/题名去重并持久化处理状态；全文解析复用浏览器登录态，支持设置 1–4 个并行任务和运行中暂停/继续，未发现 PDF 的记录保留为待检索或需人工处理。
- 全文下载优先在文章页上下文触发，以保留 Cookie、Referer 和站点生成的临时地址；Wiley 阅读器、EDP/Agronomy PDF入口和 ASHS 内嵌阅读器有独立解析分支，HTML响应不会再被记录为 PDF。
- `browser-tools/catalog.yml` 统一登记随插件安装的内置工具，首次安装或升级时会批量初始化，同时保护用户自定义版本。
- 密码框始终禁止填写；登录、验证码和机构认证应通过 `pause_for_user` 交还用户处理。
- 后台在执行前会重新校验 YAML，并要求显式的用户启动标记。

定义格式、调用方式和示例位于 [`browser-tools/`](browser-tools/README.md)。点击插件图标会在当前网页旁打开 Chrome Side Panel；在“网页工具”和“设置”中可导入或更新 YAML、填写参数，也可粘贴或从 TXT/CSV 导入一批检索词，逐词检索、提取并汇总带 `_query` 来源列的结果，再将当前或历史结果导出为 CSV/JSON；“日志 → 文献队列”负责跨来源文献清单和下载状态，不把具体站点规则写进核心。验证码、登录或权限受限项目会保留入口供用户处理后重试。需要支持 Side Panel 的 Chrome 浏览器。

## 每日签到

Side Panel 新增“签到”入口，内置科研通、GLaDOS One（glados.one）、GLaDOS Rocks（glados.rocks）三个独立签到项。它们复用各自域名的浏览器登录状态，不需要粘贴 Cookie 或保存密码。

1. 构建并重新加载 Trail 后，打开侧边栏的“签到”；旧安装可在设置中同步内置工具。
2. 使用“打开网站”完成登录，再点“立即签到”验证。
3. 按需开启各项“每日自动签到”，默认时间为北京时间 09:00，默认关闭。

Chrome 运行时每 5 分钟检查到期任务，浏览器启动后会补跑当天到期的任务。不会唤醒关机或休眠的电脑。完成结果按域名工具和当地日期分别保存；同一域名切换账户后，当天仍沿用该工具的完成记录，当前不支持同域名多账户。

自动运行只接受用户开启时的工具版本；YAML 改变后会暂停并要求重新开启。网络加载失败最多每天尝试 3 次，间隔至少 30 分钟。登录、验证码、返回结果不明或后台中断时保留工作页面，点击“打开网站”处理后重试。成功后只关闭本次创建的工作标签页。

验证命令：`pnpm exec playwright install chromium`（首次安装浏览器），然后 `pnpm run test:checkin`。测试使用隔离扩展配置及页面夹具，不使用真实账户；可通过 `TRAIL_TEST_CHROMIUM` 指定已有 Chromium 可执行文件。

## 订阅源发布

Side Panel 的“账号采集”页中的发布区把采集结果发布到一个独立的 GitHub 静态仓库（feed），由 GitHub Pages 分发，不需要本地服务端：

1. 新建一个 feed 仓库（骨架见仓库内 README），在 GitHub 仓库设置中开启 Pages（分支即内容源）。
2. 创建 fine-grained token，只授予该仓库 Contents 读写权限。
3. 在“账号采集”的 GitHub 仓库区填写 owner、仓库名、分支和 token，保存后可“测试连接”。
4. 声明了 `feed` 段的采集工具（如内置的“X 用户时间线采集”）在运行成功后会把记录自动暂存；“立即发布”把暂存记录合并到远端 `data/posts.json`（按 `平台:内容id` UPSERT、按配置封顶裁剪），并重写 `rss/all.xml`、各账号 RSS 和时间线页，同时发布关注名单 `data/follows.json`（包含账号标识、显示名及优先级，公共仓库中可公开访问）。

订阅地址形如 `https://<owner>.github.io/<repo>/rss/all.xml`。发布失败时暂存保留、错误写入状态，下一轮重试；token 只保存在本机 `chrome.storage.local`，发布目标由设置配置，工具 YAML 接触不到。X 采集依赖扩展获得 x.com 的 host 权限（用于在页面主世界调用站点自身接口），首次更新安装时会重新请求授权。

自动发布有两条路径：**实时发布**（采集完成后即尝试推送，多渠道发布请求按顺序串行执行）和**定时间隔兜底**（默认 12 小时，可设置为 1–168 小时；保存新间隔后定时器立即更新，到期若有未发布暂存则推送）。暂存上限 2000 条，触顶会在状态区提示丢弃数量。另提供**不收录转推/转发**开关；采集节奏（每用户条数、用户间隔）在采集页以句子式参数直接调整；发布失败时保留暂存，成功后仅清理本次发布涉及的记录；支持读取大于 1 MB 的 posts.json，请求超时会进入失败反馈。发布历史默认保留 20000 条（最大 50000），每源 RSS 默认 2000 条（最大 5000）。

## 定时采集

声明了 `feed`、`batch` 和 `feed.entry_url` 的工具（如内置的“X 用户时间线采集”）在“账号采集”页提供定时采集面板：

1. 导入关注账号：支持 txt（每行一个 `@handle`）或 CSV（`handle,priority,name`，带表头），按平台+账号合并去重；也可逐个添加、点 × 移除、导出或批量删除。名单保存在本地，并在发布时同步到 GitHub。
2. 开启“每 N 小时”开关（1–48 小时，默认 4）。开启即确认当前规则；内置采集规则更新会同步已有授权，自定义 YAML 变化后需重新确认。
3. 到点后后台自动打开一个工作标签页执行批量采集（复用暂停/继续/停止与瞬时错误重试），结果暂存到订阅源，配合“采集后自动发布”即可全自动更新 Pages。需要登录或验证时暂停并保留页面；失败当天最多重试 3 次、间隔 30 分钟。浏览器未运行时错过的时间在下次启动后补跑。

调度行为全部进入“日志”页（`collector.*` 事件）。

## 运行日志

Side Panel 的“日志”页展示后台关键路径的结构化日志：批量运行（开始/输入完成/重试/暂停/恢复/结束统计）、GraphQL 请求（queryId 解析来源、每次请求的状态与耗时、限流与登录态错误）、订阅源暂存与发布。日志按平台、级别、区域和关键词过滤，可导出为 JSON 或文本用于问题反馈，保留最新 5000 条；包含 token、cookie、CSRF 等敏感键的字段在写入前即被脱敏，导出内容可直接分享。调试时也可在扩展的 Service Worker 控制台看到 `[trail:区域] 事件` 形式的实时镜像。

## 当前边界

- 暂不保存完整网页正文，只保存标签页、交互事件和轻量上下文。
- `chrome://`、扩展页面、地址栏和非网页应用中的复制不会被捕获。
- 来源分级是启发式判断，用来辅助排序，不代表严格可信度评级。
- “AI 输入”只是本地导出的结构化材料，还不是自动总结。

## 本地开发

```bash
pnpm install
pnpm run build
```

运行 `pnpm run knip` 检查未使用的文件、依赖和导出。`knip.json` 显式声明扩展的后台、content script 和页面入口；报告需要结合实际调用方式审阅，不自动删除代码。此命令独立于现有构建检查，发现问题时返回非零退出码。

构建完成后，在 Chrome 扩展管理页打开“开发者模式”，选择“加载已解压的扩展程序”，加载生成的 `dist/` 目录。

测试交互捕获时，需要刷新扩展和目标网页：

1. 运行 `pnpm run build`。
2. 在 `chrome://extensions` 中重新加载 Trail。
3. 刷新需要测试的网页，让 `content.js` 重新注入。
4. 点击 Trail 侧边栏“研究路径”中的“开始记录”。
5. 在当前录制范围内选中或复制网页文本。
6. 停止记录后，在研究文档页查看“关注片段”。

## 发布

发布使用 GitHub Actions，推送 `v*` 标签会自动构建 Chrome 扩展并创建 GitHub Release：

```bash
git tag v0.2.1
git push origin v0.2.1
```

产品发布版本以 `package.json` 为唯一来源，扩展清单、锁文件、设置页和发布包保持一致。更新版本使用：

```bash
pnpm version 0.2.1 --no-git-tag-version
```

该命令更新 package.json，并自动同步扩展清单；pnpm 锁文件不记录根包版本。随后补充对应的更新日志，发布前运行 `pnpm run build` 与 `pnpm exec playwright test`。每次构建都会检查以下版本号，防止代码更新而扩展版本不变：

- `package.json`
- `public/manifest.json`
- `CHANGELOG.md` 中的 `## [x.y.z]`

Release 产物：

- `trail_v0.2.1_chrome.zip`（文件名跟随产品版本）
- `checksums.txt`

zip 内部直接包含 `manifest.json`、`entries/`、JS、assets 和 icons，可用于 Chrome Web Store 上传或手动分发。

网站 YAML 中的 `version` 是独立的**规则修订号**，不是扩展版本；只有该网站规则改变时才递增。`schema_version` 标识配置格式，catalog 的整数 `version` 标识目录修订，都不作为产品版本展示。

设置页会显示随当前 Trail 发布的内置版本，以及自定义工具对应的可用内置规则。同步不会覆盖自定义修改；点击“使用内置版”会先另存自定义备份，再切换到内置规则。

## 提交规范

使用 Conventional Commits：

```text
feat(scope): message
fix(scope): message
chore(scope): message
```

安装本地 Git hooks 后，会在提交前运行项目检查，并在提交时校验 commit message：

```bash
pnpm run install-hooks
```

采集预算支持按平台配置浏览量、主页/详情次数上限和 1–3600 秒访问间隔。次数上限 0 表示只使用浏览量限制，任一额度耗尽即暂停。日志记录配置变更、预留用量与等待时间、取消退款、访问结果与耗时、验证拦截和重试，便于导出对比；验证或拦截不等于封号，默认值不代表平台认可的安全阈值。日志最多保留 5000 条，长期比较请定期导出。
